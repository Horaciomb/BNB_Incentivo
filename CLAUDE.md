# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Small dashboard app for a sales-incentive campaign ("Cierre de Agosto 2026", BEX/BNB). Frontend and backend live in the **same root directory** (no `frontend/`/`backend/` subfolders):

- `src/` — React 19 + Vite app. `src/App.jsx` holds nearly all UI logic (~700 lines), `src/api.js` is the fetch wrapper, `src/main.jsx` is the entry point.
- `server.py` — single-file FastAPI backend at repo root.

## Running the app

- Frontend dev server: `npm run dev` → Vite on **port 5175** (hardcoded in `vite.config.js`, not Vite's default 5173). Proxies `/api/*` to `http://localhost:8000`, or to `BACKEND_PORT` if that env var is set (other apps on this machine sometimes hold 8000).
- Frontend build: `npm run build`. Preview build: `npm run preview`.
- Backend: `python server.py` (or `uvicorn server:app`) → runs on **port 8000**. Activate the venv on Windows with `venv\Scripts\Activate.ps1`, not a POSIX `bin/activate`.
- Both must be running together for live data; the frontend falls back to hardcoded static data if the backend is unreachable (see below).
- `requirements.txt` está clavado a lo que el venv **compartido** de producción ya tenía (ver Deployment), no a las versiones del venv local. Ojo con `pandas`/`openpyxl`/`requests`, agregados el 09-sep-2026 para leer la planilla: se pinearon a las del servidor (`3.0.2`/`3.1.5`/`2.33.1`), que eran **más nuevas** que las de la máquina de desarrollo — pinear a las locales las habría degradado para las otras ~8 apps del venv compartido — the local venv (`venv\Scripts\pip.exe freeze`) may run newer `fastapi`/`uvicorn` than what's pinned here; that's expected, don't "fix" it by bumping the pins without checking prod first.
- No test suite, linter, or formatter is configured anywhere in this repo. There are two **verification scripts**, though, and both are meant to be run by hand:
  - `npm run verificar:reporte` (`scripts/verificar_reporte.mjs`) checks the Excel report against the live API without a browser — it reuses `construirHojas()` from `src/export.js`, which is exported precisely so this can run outside the browser. **Run it whenever a campaign is added to `campanas.json`**: the per-project columns come from `proyectos[].etiqueta`, so that's when the report breaks. `--api <url>` points it at another backend, `--guardar <dir>` keeps the generated `.xlsx` instead of deleting them.
  - `.\deploy\verificar_produccion.ps1` checks the deployed app from outside — see Deployment below.

Si se olvida alguno **la app no se cae y `/api/health` sigue diciendo `"database": "configurada"`** (sólo comprueba que las variables no estén vacías, no que conecten): `_calcular_incentivos()` atrapa el error de conexión y sirve `FALLBACK_ROSTER`. La señal real es `es_respaldo: true` en `/api/incentivos/<id>` (banner de «datos de demostración» en la UI) y el `Error armando el roster real` en `api\stderr.log`. Ese mismo mensaje cubre ahora la planilla ilegible, no sólo la BD caída.
- Redeploy: `.\deploy\deploy-backend.ps1` (guards against deploying an uncommitted tree; installs into the **shared** BNB venv) and `.\deploy\deploy-frontend.ps1` (builds with `vite.config.js`'s production `base: '/convocatoria/bnb/'`, uploads to a temp folder, merges via `robocopy /MIR /XD api` — a full-folder swap like rrhh-app's would delete the co-located backend).
- **After any deploy, run `.\deploy\verificar_produccion.ps1`.** `deploy-backend.ps1` only curls `/api/health` on `127.0.0.1:8221` **inside** the server, which passes even when the Caddy route is gone — exactly the 28-ago-2026 failure: backend alive, app 404 for everyone. The verifier hits the public URL through Caddy and checks the route (200 with the block's own CSP and no `Server` header, 301 without the trailing slash), the build's assets, `/api/health`, `es_respaldo: false` on every visible campaign, and that CORS rejects a foreign origin. `-Url` points it elsewhere; it exits non-zero on the first failure count.
- **`requirements.txt` pins `fastapi`/`uvicorn` to what the shared venv already had** (`0.136.3`/`0.49.0`), not newer versions — a plain `uv pip install -r requirements.txt` on a shared venv silently upgrades every other app sharing it on their next restart. Check `uv pip list --python C:\uv-envs\bnb\Scripts\python.exe` before ever bumping these.
- The `/convocatoria/bnb/*` Caddy block is the **only app on this server whose route doesn't follow the `/<unit>/<app>/` convention** (everything else, including 4 other BNB apps, is `/bnb/<app>/`) — a deliberate user choice made with the inconsistency flagged, not an oversight. `deploy/caddy_snippet_convocatoria.txt` has the exact block if it ever needs restoring.
- **El bloque de Caddy se perdió una vez (28-ago-2026) y puede volver a pasar.** Alguien editó `C:\Caddy\Caddyfile` partiendo de una copia vieja (~22-23 ago) para aplicar unas correcciones de seguridad, y guardó sin backup: se borraron de golpe los bloques añadidos entre esa copia y el 27-ago — `/convocatoria/bnb/` entre ellos, además de 4 apps de otras unidades. Síntoma: **404 con `Content-Length: 0` y la CSP genérica del sitio** (la que incluye `unpkg.com`), idéntica a la de una ruta inexistente; y `/convocatoria/bnb` sin barra devolviendo 404 en vez de 301. **Desde el 05-sep-2026 ese síntoma ya no discrimina nada por sí solo**: la regla global nueva `@no_publicos` (404 en `/cirpob/*`, `/extraer_negocios/*`, `/api/*`, `/frontend/*`, `/mapas/*` a nivel de raíz) responde con cabeceras idénticas — mismo `Content-Length: 0`, misma CSP con `unpkg.com`, mismo `Server: Caddy` — verificado el 07-sep-2026. La prueba fiable pasa a ser **en positivo**: `GET /convocatoria/bnb/` debe dar **200 con la CSP propia del bloque** (`script-src 'self'`, sin `unpkg.com`) y **sin cabecera `Server`** (el bloque hace `-Server`), y `GET /convocatoria/bnb` sin barra debe dar **301**. Restaurar con `.\deploy\reponer_caddy_convocatoria.ps1` (se sube a `C:\Caddy\` y se ejecuta allí), luego `caddy validate` y `caddy reload` — nunca recargar sin validar, el Caddyfile es compartido por ~20 apps.
- **Los roles y permisos de PostgreSQL no entran en el respaldo diario del VPS** (`pg_dumpall --globals-only` exige superusuario y `bex_ingeniero` no lo es; arreglo comiteado pero sin desplegar al 05-sep-2026). Si alguna vez hay que reconstruir el servidor, `bex_app` y `bex_ingeniero` se recrean a mano — no se recuperan del zip.
- `deploy/insertar_caddy.ps1` **ya no funciona**: busca el comentario `# Ocupacion del VPS por unidad`, que desapareció en ese mismo incidente. `reponer_caddy_convocatoria.ps1` lo reemplaza — ancla en `handle_path /comun/* {`, toma el texto del bloque de `C:\Caddy\Caddyfile.bak_rumbo_geoloc` (27-ago) y hace el splice a nivel de bytes vía Latin-1 (codepage 28591) en vez de releer como UTF-8, porque el Caddyfile arrastra mojibake previo y una lectura UTF-8 lo convertiría en `U+FFFD` dañando los otros bloques. Verifica que la cuenta de bytes no-ASCII no cambie y revierte solo si cambia.

## Backend / database

`server.py` lee de **tres fuentes distintas**: la planilla de Personal para el roster, y dos bases PostgreSQL separadas en el mismo servidor (`10.0.0.2:5432`) para la producción.

| Fuente | Credencial | Uso |
|---|---|---|
| Planilla de Personal (Google Sheets publicado) | `URL_PERSONAL`, o la URL por defecto del módulo | **Roster de afiliadores** (nombre, CI, ciudad, supervisor, estado, celular) |
| `bnb_bd` | `bex_ingeniero` / `RRHH_PG_PASSWORD` | `fact_afiliaciones` crudo — producción real de la campaña BNB |
| `bille_bd` | `bex_ingeniero` / `RRHH_PG_PASSWORD` | `fact_afiliaciones` crudo — producción real de la campaña BILLE |

**El roster ya NO sale de `rrhh_bd`** (cambio del 09-sep-2026, ver `personal/__init__.py`). Salía de `rrhh_bd.empleado_unidad` y perdía a todo el que RRHH no hubiera cargado ahí: eran 22 afiliadores con producción real, el 26,5% de las afiliaciones BILLE de la campaña de septiembre, y dos bonos sin pagar. La planilla los cubre a los 22. Es la misma conclusión a la que ya había llegado P9 en el repo `procesos`, que abandonó `dim_ejecutivo` por esta fuente. Como consecuencia la app **ya no usa el rol `bex_app` ni la variable `DB_PASSWORD`**.

- **BILLE is not a separate business unit — it's a campaign of BNB.** Ambas campañas se miden contra el *mismo* roster, cruzando por celular (`codigo_bex` de la planilla). No se filtra por la columna `campana` de la planilla: quien está en BILLE puede producir QR y viceversa.
- In `bnb_bd`/`bille_bd`, the column `fact_afiliaciones.codigo_bex` actually stores the **phone number** (not a business code) — that's the join key against `empleado_unidad.telefono`. This is a documented gotcha from the sibling RRHH migration project, not a mistake in this code.
- Counts are filtered by exact `fecha_hora_envio` in the campaign window (`CAMPANA_DESDE`/`CAMPANA_HASTA_EXCLUSIVO`, currently 24–31 Aug 2026), **never** read from `rrhh_bd.actividad_afiliacion_mensual` — that table aggregates by calendar month and would overcount, since the campaign is a partial-month window.
- Dedup ("producción no duplicada" per `correo.txt`) is `COUNT(DISTINCT id_afiliacion)`.
- `bex_ingeniero` is a privileged migration/reporting role (also used by the separate `rrhh-app`/`Lab` projects at `C:\temp\RRHH\`) — reused here read-only (`conn.set_session(readonly=True)`) rather than provisioning a new role, per explicit user decision. Its password lives only in the `RRHH_PG_PASSWORD` env var, shared with those other projects — never hardcode or version it.
- **Si `RRHH_PG_PASSWORD` está vacía, o si la planilla no se puede leer, el backend sirve `FALLBACK_ROSTER`** y marca `es_respaldo: true` — nunca datos reales a medias (p.ej. nombres reales con cuentas en cero porque una fuente no respondió). Es el comportamiento esperado en desarrollo local sin acceso, no un bug. `planilla_personal.py` reintenta 3 veces, cae a su caché en disco (`dat/cache/personal.xlsx`, gitignoreado: es la nómina completa) y recién ahí lanza.
- Un celular repetido entre dos personas se omite en vez de contarse dos veces — el set `vistos` en `_roster_desde_bd()`. Hoy la planilla no trae ninguno, pero la guarda se mantiene: duplicarlo sería pagar dos bonos por el mismo trabajo.
- **`estado` se toma de `cargar_demografia`, no de `cargar_roster_contratos`.** El segundo resuelve la persona por el contrato con la fecha de ingreso más reciente, que **no es el vigente**: quien ascendió a supervisor conserva el contrato viejo de activador con fecha posterior y sale marcado INACTIVO. Con eso Claudia Shaskia Calle Nina, supervisora activa, aparecía inactiva y su bono no se calculaba. `cargar_demografia` ordena por `(activo, ingreso)` antes del `keep="last"` y es la única fuente correcta del estado.
- **Cruce inverso (`sin_roster`).** `_detectar_sin_roster()` lista los celulares que produjeron en la ventana y no están en el roster; viaja siempre en la respuesta (aunque vacío) y el frontend lo muestra como banner. Sin esto el caso es invisible: la app solo mira roster → producción, así que un afiliador que la planilla no tenga desaparece del tablero sin ninguna señal. Así se perdieron los dos bonos de agosto/septiembre 2026.
- CORS is restricted to an explicit allowlist (`ORIGENES_PERMITIDOS` in `server.py`): the production origin plus the two localhost forms of the Vite dev server, `GET` only, no credentials. Nothing actually depends on it — in production Caddy serves the frontend and the API from the **same** origin, and in dev Vite proxies `/api` — so it only covers hitting the backend directly from the dev server.
- Un `.mcp.json` en la raíz declara conexiones MCP Postgres de solo lectura a `rrhh_bd`, `bnb_bd` y `bille_bd` (misma credencial `bex_ingeniero`/`RRHH_PG_PASSWORD`) para poder inspeccionar el esquema real desde Claude Code — hay que reiniciar Claude Code para que las tome. `rrhh_bd` ya no la usa la app, pero sigue sirviendo para investigar discrepancias contra la planilla.

## Campaign rules — `campanas.json` is the single source of truth

The app serves **several campaigns from one URL**, picked from a `<select>` in the header. All rules (window, per-project targets/prizes, double-goal bonus, supervisor bonus) live in **`campanas.json`** at the repo root, deployed to `C:\Proyectos\BNB\web\convocatoria\api\campanas.json`. The frontend receives them through the API and duplicates no target or prize — the old `META_CONFIG` / `CAMPAIGN_RULES` pair is gone.

Adding a campaign = appending an object to `campanas.json`. Nothing else changes: no Python edit, no frontend rebuild. `server.py` re-reads the file **by mtime**, so editing it directly on the server takes effect **without restarting the nssm service**. A malformed file fails loudly (`/api/health` reports `campanas_cargadas: 0` and `error_config`), it never degrades silently.

Per campaign: `id`, `nombre`, `subtitulo`, `desde`/`hasta` (inclusive, ISO), `periodo_texto`, `proyectos[]`, `doble`, `supervisor` (or `null`).
Per project: `key` (`BNB`/`BILLE` — indexes the counts), `etiqueta` (**visible label**), `bd` (`bnb_bd`/`bille_bd`), `tema` (`bnb`/`bille`, picks the Tailwind palette), `meta`, `premio_bs`. The array order is the tab order.

- **`etiqueta` is decoupled from `bd` on purpose**: the September campaign shows `bnb_bd` production as **"QR"**, the August one shows it as **"BNB"**, per each official email.
- `hasta_exclusivo` (what goes into the SQL `fecha_hora_envio <` filter) is derived as `hasta + 1 día` — never write it in the JSON.
- **Visibility window**: `/api/campanas` serves campaigns that are running, upcoming, or finished less than **3 months** ago (`MESES_HISTORICO` in `server.py`). Older ones stay in the file but return 404. Past campaigns are **recalculated live** from `fact_afiliaciones` — there are no snapshots, so a later correction in the source data changes the history.
- Results are cached in memory per campaign: 5 min while running, 1 h once finished.
- Current campaigns (per `correo.txt`): *Cierre de Agosto* 24–31 Aug 2026 (BNB 60 / Bille 70, Bs.150 each, both → Bs.300) and *Incentivo Inicio de Mes* 1–6 Sep 2026 (same targets, plus **Bs.20 per team member who earns any bonus** for supervisors — counted **once per person**, not once per bonus, so a Bs.300 double-goal earner still contributes Bs.20).

Fallback data is no longer duplicated either: a single `FALLBACK_ROSTER` in `server.py` serves any campaign, and the response marks it with `es_respaldo: true` so the UI shows an explicit "datos de demostración" banner. **The frontend has no static dataset anymore** — if the backend itself is unreachable it shows an error with a Retry button rather than inventing numbers.

Frontend layout: `src/App.jsx` is the orchestrator (state, fetch, tabs); `src/campaign.js` holds the theme map and the shared prize logic; sections live in `src/sections/`, shared widgets in `src/components/`. Tailwind v4 cannot see runtime-built class names, so every theme class is written in full in `campaign.js` — never build one with a template literal.
